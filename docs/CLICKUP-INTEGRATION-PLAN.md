# ClickUp tasks on the Focus Island board

Analysis and implementation plan, 2026-10-24. Planning only: no ClickUp account was connected, no tasks were fetched, and no app integration was implemented.

## Recommendation

Add manual, read-only ClickUp import and sync alongside Jira. First prove the browser sign-in and complete assignment-discovery path through **ClickUp's official hosted MCP service**. Its public metadata supports a secretless client, but metadata is not evidence that Focus Island can finish consent or retrieve every assigned task. Keep that proof ahead of database and UI work; the Jira consent failure demonstrates why this gate matters.

The intended flow is **Integrate ClickUp → browser consent → return to Focus Island → Sync my ClickUp tasks**. No CLI, copied token, local proxy, or Focus Island server. Use one ClickUp account and one selected Workspace initially; Jira can stay connected simultaneously. No automatic polling, writeback, comments, webhooks, attachments, or cross-provider task merging in the first version.

**Phase 0 exit gate:** a small native prototype must complete registration, consent, an exact loopback callback, token exchange, identity/Workspace selection, exhaustive assignment discovery, and task detail retrieval with `read` only. Check cancellation, restart, expiry, reconnect, and account-side revocation. Public metadata currently advertises only the authorization-code grant and no revocation endpoint; token lifetime/refresh behavior and programmatic revocation remain unverified. Do not invent refresh support. If any gate fails, stop product integration and record the provider restriction. A manually entered personal token is an explicit alternative requiring a product decision because it contradicts the requested one-button setup; it is not a silent fallback.

Reuse the existing PKCE/state, callback validation, bounded HTTP, and Keychain patterns in [JiraAuthorization](../Sources/FocusCore/JiraAuthorization.swift) and [JiraOAuthCallback](../Sources/FocusCore/JiraOAuthCallback.swift). Extract only transport/security primitives actually needed by both clients, preserving Jira tests. Keep provider endpoints, identity, scopes, and response decoding separate. Use a ClickUp-specific Keychain service and UserDefaults key. Never log tokens, authorization URLs, descriptions, or private task identifiers. Clearing credentials must invalidate pending saves and imports.

## Task discovery contract

The REST API establishes the desired behavior and an alternative adapter contract; it is **not** an authorized fallback for an MCP token:

1. Resolve identity with `GET /api/v2/user` and authorized Workspaces with `GET /api/v2/team`. Select a Workspace explicitly when more than one is available; `team` is the API's Workspace terminology. Never infer “me” from a name or email search. [User](https://developer.clickup.com/reference/getauthorizeduser), [Workspaces](https://developer.clickup.com/reference/getauthorizedteams)
2. Request `GET /api/v2/team/{workspaceID}/task` with `assignees[]={userID}`, `subtasks=true`, `include_closed=false`, `order_by=id`, and `page=0…`. The endpoint returns at most 100 tasks per page. Finish using the verified response termination contract; an arbitrary cap must report incomplete discovery, never success. Deduplicate by stable task ID and reject repeated/non-advancing pages. [Filtered Workspace tasks](https://developer.clickup.com/reference/getfilteredteamtasks)
3. Include assigned subtasks independently of their parent's assignment. A subtask's `parent` identifies its immediate parent; it is not a reason to import the parent or turn a remote subtask into a local criterion. [Subtask representation](https://developer.clickup.com/docs/faq)
4. Define unfinished as status type outside `done` and `closed`, including unstarted and active work. ClickUp distinguishes Done (still open) from Closed, so `include_closed=false` alone is insufficient. Filter by status type, never translated/custom display names; verify MCP exposes that distinction. Preserve the source status badge independently from the local board column. [Status semantics](https://help.clickup.com/hc/en-us/articles/6309452618647-Manage-task-statuses), [Status types](https://developer.clickup.com/docs/filter-views)
5. Fetch details by stable task ID before import. Custom IDs are display values; REST requires extra parameters when looking up a custom ID. Prefer bounded Markdown/plain-text descriptions; leave attachments and linked Docs in ClickUp. [Get Task](https://developer.clickup.com/reference/gettask)
6. Do not enumerate Lists as the primary discovery strategy. List reads default to a task's home List; `include_timl=true` includes tasks added from another List. A task appearing in several Lists still creates one card. Verify Workspace/MCP discovery covers this case, including restricted home Lists, before claiming completeness. [Get Tasks](https://developer.clickup.com/reference/gettasks)

MCP must satisfy this contract with deterministic parameters and complete pagination. If its authenticated-user identity or assignment search is unavailable, browser sign-in alone does not pass Phase 0. A mutable remote dataset also means pagination is not a transactional snapshot: repeated manual sync must be idempotent, and absence from discovery never deletes a card.

Keep calls serialized and cancellable. Reuse complete discovery snapshots where possible instead of fetching every detail twice. MCP limits can be much lower than REST: without Everything AI, Free Forever has 100 and Core/Unlimited 300 calls per rolling 24 hours, per Workspace/client; `initialize` and `tools/list` do not count. Respect `RATE_LIMIT_EXCEEDED`/`retryAfter`. REST limits are per token, starting at 100/minute, and return HTTP 429 plus reset headers. Show a retry time and retain cached data; avoid automatic retry loops. Phase 0 must also estimate calls for the expected task count and sync frequency: discovery pages + uncached detail reads + linked tasks outside discovery + identity checks. If a complete sync exceeds the Workspace budget, report that limitation before building the integration; silently capping imports is not acceptable. [MCP limits](https://developer.clickup.com/docs/connect-an-ai-assistant-to-clickups-mcp-server), [REST limits](https://developer.clickup.com/docs/rate-limits)

## Minimal local model and preservation

The existing implementation has provider-specific [JiraModels](../Sources/FocusCore/JiraModels.swift), [JiraTaskService](../Sources/FocusCore/JiraTaskService.swift), and [JiraCoordinator](../Sources/OpenIslandApp/Focus/JiraCoordinator.swift). Follow those seams with `ClickUpModels`, `ClickUpProviding`, `ClickUpMCPClient`, `ClickUpTaskService`, and `ClickUpCoordinator`; do not introduce a generic provider framework or migrate existing Jira links.

Add a `v8` migration to [FocusStore](../Sources/FocusCore/FocusStore.swift) with `clickup_task_links`: local `taskId` primary/foreign key, `workspaceID`, stable `remoteTaskID`, optional custom display ID, validated source URL, home List context, optional parent ID, remote status/type, assignee IDs, remote update time, last successful refresh time, and availability. Store remote identifiers as strings. Enforce uniqueness on `(workspaceID, remoteTaskID)`; imports create a new local task and cannot attach a second provider to an existing card. Keep title/description in the existing task columns.

Extend [BoardSnapshot and BoardService](../Sources/FocusCore/BoardService.swift) with ClickUp links, source-field edit protection, and deletion cleanup. A small `isSourceLinked(taskID:)` check is justified where both providers require identical UI protection; the providers' models and sync logic remain separate.

Preserve these existing Jira guarantees for both providers:

- Collect and validate the complete new-import batch before one database transaction. A failed page/detail or cancellation must not insert a misleading partial set.
- Refresh only source title/description and metadata, never column/order, completion, notes, criteria, prompts, repository folder, sessions, timers, activity, or reports. An editor opened before refresh cannot overwrite refreshed source fields.
- Compare the expected link before applying results. Late responses cannot recreate detached/deleted links or survive Forget/account changes. Refresh only links for the connected Workspace.
- Refresh linked tasks missing from discovery individually: completion, reassignment, and access loss are different from deletion. Keep cached text; mark unavailable only after a confirmed access/not-found result, not a timeout or rate limit. Report partial refresh honestly.
- Before upgrading an existing database, make one consistent `before-clickup-*.sqlite` backup. Migration failures preserve the original database; reopen does not make another backup. Keep import disabled for in-memory fallback storage. No automatic backup restore or downgrade over subsequent work.

## User interface

Settings → Setup adds a separate ClickUp connection card: **Integrate ClickUp**, connected identity/Workspace, **Sync my ClickUp tasks**, **Reconnect**, and **Forget**. Connect verifies access but does not silently populate the board. Explain an empty result, an incomplete sync, and rate limiting distinctly from “not connected.”

The board gets a ClickUp menu matching Jira: sync assigned tasks into Backlog, selected import into Backlog/Todo with optional repository folder, reload discovery, and refresh linked cards. A source badge opens the task in ClickUp and shows remote status, last successful refresh, and unavailable state. Existing local progress remains independent. Retain Jira controls and show which provider owns an operation/error.

**Forget** cancels work and clears only ClickUp metadata/Keychain credentials, keeping cards and history. Explain that local forgetting is not server-side revocation; link to ClickUp's account settings for connected-app revocation until a supported revocation API is verified. **Reconnect** reauthorizes and verifies the account/Workspace before sync; switching scope never refreshes old cards with the wrong identity. **Detach** keeps the latest text and local history but makes source fields editable; deleting a local card never deletes the ClickUp task. ClickUp documents account-side OAuth revocation. [Revocation guidance](https://clickup.com/blog/how-to-use-clickup-mcp-server/)

## Implementation evidence — v0.7.0

Phase 0 passed on 2026-10-24: Focus Island’s registered native public client completed real browser consent, PKCE exchange, and the exact loopback callback with issuer/state validation. Read-only identity and one selected Workspace were verified. The grant returned an expiring access token without a refresh token; this release explicitly asks for reconnection on expiry.

The live Workspace returned 93 assigned tasks on one complete page. Fixed `task/get_many/getBulkTasks` reads in batches of ten returned every discovered ID; six home-List reads supplied status types. A large response was explicitly truncated, so the production client recursively splits bounded batches and rejects a truncated single-task response. Negative additional assignee IDs observed in bulk metadata are preserved; the current-user filter still matches the verified user ID exactly. Only fixed read tools/operators are callable.

Production transport fixtures cover JSON/SSE parsing, pagination, repeated pages, truncation, partial sets, scope mismatch, auth/session expiry, read limits, and missing tasks. Private recorded live responses passed the production decoder and repeat imports into disposable SQLite storage, including a local note/completed card, refresh, detach, and forget. Private response bodies and credentials are not committed. A native sign-in/read helper supplied the live proof; the packaged app’s entire sign-in/sync flow has not yet been exercised live.

Migration v8 and stale-editor tests preserve existing Jira links, task history, Claude/Codex sessions, criteria, prompts, timers, activity, and day plans. App fixtures cover explicit sync, repeat imports, reconnect/forget, cancelled work, and disabled fallback storage. Rendered synthetic Setup/import/detail/board screenshots confirm controls and source badges.

Live pagination beyond one page, assigned subtasks, Done/Closed tasks, multiple-List permission edge cases, token expiry, and account-side revocation were not independently exercised. Fixtures cover the deterministic behavior; they are not claims of live acceptance. One Workspace is selected in consent; there is no multi-Workspace aggregation. Personal-token setup, a hosted OAuth broker, scheduled sync, and remote writes remain out of scope.
